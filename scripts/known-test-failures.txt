# 已知失败用例基线（历史债锚定）
#
# 用法：scripts/check-xcresult-failures.sh 把本次 xcresult 的失败用例与本文件比对，
# 命中基线 → 只告警放行；基线外的新增失败 → 直接判红。于是不再出现"CI 绿但用例在失败"，
# 也不必一次性修完所有历史债。
#
# 格式：`<label>:<TestClass>/<testMethod>`，label 与 ci.yml 传入的一致（iOS / macOS / UI）。
# macOS 两个分片共用 macOS label；用例换分片不影响本文件；方法名写不写 () 都识别。
# 四种粒度，从紧到松——通配范围越大掩盖越多，能收紧就收紧：
#   `macOS:Foo/testBar`        精确一条，用于确定性失败（断言写错、标识符缺失）
#   `macOS:Foo/testBarBaz*`    同组飘移豁免：CamelCase 前两词相同的一族里只要飘过一次，整组按飘移处理
#   `macOS:Foo/*~crash`        只豁免崩溃形态（failureText 含 segv/crashed with signal/Crash:）；
#   `macOS:Foo/*~timeout`      只豁免超时形态（failureText 含 exceeded execution time allowance）。
#                              这两类的责任用例是 xcresult 归因出来的：进程被杀时记在"当时在跑"的
#                              方法上，每轮受害者都不同（崩溃见 AgentOrchestrator，超时见 UI），逐条
#                              追不完。同一个类里新增的断言失败、以及别的形态照旧判红；被豁免的条目
#                              仍会打印在门输出与 step summary 里，形态名跟着条目后缀走。
#                              后缀也能挂在精确条目上（`macOS:Foo/testBar~crash`），只豁免这一条
#                              用例的那一种形态，用于受害者已经收敛到单个方法的类。
#   `macOS:Foo/*`              整类豁免，只在该类过半方法都在飘（断言/超时也算）时使用；
#                              它连该类新增的真实失败一起放过，代价最大，能用上面三种就不要用它。
#
# 维护约定：
# - 修好一条就删一条。加条目只允许发生在"严格门首次暴露闸门修好前就存在的失败"这一次性
#   锚定里；此后想让 PR 变绿必须改用例或改产品代码，或用 -skip-testing: 显式跳过并注明原因。
#   `*~crash` / `*~timeout` 例外：它们锚的是"归因随机"这件事，不是某条用例，所以只在该类第一次
#   出现该形态失败时加，加了就要去查那个崩溃/那次超时；类里真正要修的用例仍按精确条目记，别
#   指望形态豁免替你记账。超时豁免目前只给 UI job：XCUITest 冷启动 app 要 60-80s，120s
#   allowance 正好压在临界值上，哪条越线每轮随机（四轮换了 5 个受害者）；单测 job 的超时逐条记，
#   不用豁免。第九轮（main@5090a91）把这条判断换成了更根本的解释——单测超时不是"归因随机"，
#   是"耗时压在 60s allowance 临界值上"，而这些耗时本该在 CI 里根本不发生：
#   - ShortcutsToolTests 换受害者：testCreateCopyToClipboardSuccess 十轮里飘 5 次，
#     testCreateOpenUrlSuccess 首次越线；该类三处 testCreate*Success 真实耗时在 4.5–58.7s
#     之间波动（同一轮 testCreateShowTextSuccess 16.1s），越不过去纯属运气。
#   - RateLimiterTests 两条 61 秒真实等待，在 iOS 和 macOS 两边都必然越线。
#   共同根因是 `environment["CI"]` 守卫读不到东西：GitHub Actions 的 CI 变量不传进测试进程
#   （macOS 侧的证据是 .github/macos-test-durations.json 里 RateLimiterTests 仍记着 132.5s，
#   两条 61 秒等待确实在跑），模拟器里唯一有效的信号是同 target 用了 60 多处的
#   `SIMULATOR_DEVICE_NAME != nil`（该轮 Location/Contacts/Alarm 分别 skipped 22/15/18 条）。
#   所以本轮删掉 5 条锚点而不是再加豁免：设备相关的 ShortcutsToolTests 3 处按既有写法补上
#   模拟器条件；wall-clock 依赖的 RateLimiterTests 2 条改用 `RateLimiter.acquireChat(now:)`
#   时间接缝，回拨 61 秒代替真实等待，iOS/macOS 两边都能跑而且不再超时。
#   NativeEngines/WhisperASR/MLXVision 那批超时锚点同源于产品侧的无界等待（当时记为"另开 PR
#   单独评估"），现在三处都改成有界兜底，机制各不相同，别当成同一种"超时豁免"：
#   - NativeASREngine：SFSpeechRecognizer.requestAuthorization 的回调在模拟器上永不触发
#     （本地 iPhone 17 复现，把 maximum allowance 放到 150 秒仍无返回）。授权窗口 5 秒、识别
#     任务窗口 30 秒，到点分别返回"授权回调超时"/取消任务并抛 asrRecognitionFailed。用例侧本来
#     就接受这个错误，于是同一条用例从 >60s 越线变成 iOS 0.022s（模拟器 recognizer 不可用，走更
#     早的分支）、macOS 5.013s（真把 5 秒授权窗口跑满）通过。WhisperASR 不可用时降级到它，同源。
#   - NativeTTSEngine：真机制不是"没有音频"。AVSpeechSynthesizer.write 在模拟器上一直在交付
#     PCM 帧，只是表示结束的 nil 永不到来，所以每条合成用例都要白等满 30 秒定长兜底
#     （本地实测 30.03–30.12s）。改为"帧间静默 5 秒即收尾"后是 5.1–6.7s，而且交付的是真音频；
#     顺手删掉那个读不到 CI 变量、从来没生效过的 environment["CI"] stub。
#     `testTTSEngineSynthesizeWithVoiceId` 那条精确锚点就是这里来的：30 秒定长正好压在 allowance
#     临界值上，偶尔越线、偶尔压线通过。
#   - NativeVisionEngine：本地 1.3s 就正常返回，只有 CI runner 上挂死，故 5 个子请求各加 10 秒
#     空结果兜底。第一次只加窗口没用——`VNImageRequestHandler.perform` 是同步阻塞调用，
#     `describe` 的五个 `async let` 把它留在 Swift 协作线程池上跑，runner 的池只有核数量级的
#     线程，一挂死整个池被抽干，兜底的 resume 自己都排不上线程（PR #59 第一轮 CI 正是这样：
#     iOS 9 条 + macOS 2 条 `exceeded 1 分钟`，窗口形同不存在）。真正的修法是 perform 挪到
#     独立队列，且队列 `maxConcurrentOperationCount = 5`：挂死的 perform 永不交还线程，不设上限
#     就变成了每调一次 `describe` 泄漏 5 条线程。这处的收益本地仍测不出来（本机 Vision 不挂），
#     只能由 CI 轮次验证；但它同时也是生产侧的上界——一次 Vision 服务卡死原本会冻结整个 App 的
#     async 工作，而不只是这一个请求。
#   据此删 iOS 8 条 + macOS 7 条锚点。iOS 一侧由本地全量 run 验证（3193 passed / 36 failed，
#   其中 35 条命中基线，多出的 1 条是 SemanticMemoryStoreTests 的本地偶发，单跑该类通过，按
#   "复现 >=2 次才收"不收）；macOS 一侧本地只跑了这三个类（40 tests 0 failures、无 exceeded
#   execution time 行），删条目的依据是 main@5090a91 两个 macOS 分片 job 日志里同形的挂死记录
#   ——MLXVision 2 条、NativeEngines 的 ASR/facade/vision* 共 8 条、WhisperASR 2 条全部
#   exceeded，而 4 条 testTTSEngineSynthesize* 正好卡在 30.02–30.108s，与上面那条机制吻合。
#   MCP/SSE 族 10 条（同一批 5 个方法在 macOS / iOS 各记一条）修的是四处不同的东西：
#   - SSETransport 的分帧：`URLSession.bytes(for:).lines` 不会为结尾的空行再产出一个 ""，于是
#     "服务器发完最后一条事件就关流"这种形态在解析循环里永远等不到事件边界，那条挂起的事件整条
#     丢掉。改成流正常结束时把未派发的缓冲补发一次（异常路径不补发，那里的事件可能只收了一半）。
#     三条失败同源：MCPClientTests.swift:679 `("0") is not equal to ("1") - 应仅收到 1 条 message
#     事件`，以及 SSETransportTests.swift:248 / :181 两条都停在 `connectionFailed("SSE POST 端点未就绪")`
#     ——endpoint 事件同样被丢了，postEndpoint 从未被设置。main@632e087 的 iOS unit-tests 日志里
#     这 5 条都在，macOS 侧分布在两个分片（分片 1 四条，分片 2 是 hijack 那条的两个断言），
#     file:line 与断言文案跟本地跑出来的一致；本地按方法挑出来跑也是 5 条全红。
#     同源的 testHandleSSEEventCrossOriginEndpointRejected 改前一直是绿的，那是假绿：它只断言
#     postEndpoint 为 nil，事件丢失恰好满足。补发之后事件才真的进到同源校验里被拒（本地日志有
#     `[MCPSecurity] 检测到 MCP endpoint 劫持尝试：SSE=http://localhost:9999/sse, endpoint=http://evil.com/api`）。
#   - 同源校验的端口口径：旧写法 `(url.port ?? base.port) == (base.port ?? url.port)` 在"只有一侧
#     写了端口"时两侧退化成同一个值——SSE 连 `http://localhost/sse`（隐式 80）、endpoint 指
#     `http://localhost:9999/messages` 会被放行，带 Authorization 头的后续请求就交给了 9999 端口。
#     换成按 scheme 补默认端口后拼出 `scheme://host:port` 再比，新增
#     `testHandleSSEEventEndpointPortMustMatch` 把拒绝和接受两个方向都钉住。诚实记一句：这次 10 条
#     锚点没有一条是它修好的。我最初按"相对 URL 取不到 scheme，所以合法 endpoint 被误判成劫持"
#     改的它，实测那 3 条照旧红——`URL(string:relativeTo:)` 经 base 就能拿到 scheme/host/port，
#     误判的前提不成立；真正的丢事件原因是上面那条 EOF 补发。这处留着是因为它补的是一个真漏洞。
#   - MCPDiscoveryService 的前后台状态机：`setForegroundActive(false)` 停掉 browser 与 Timer 却留着
#     `isScanning == true`，回前台时 `startScanning()` 的 `guard !isScanning` 把恢复挡死，于是
#     MCPDiscoveryServiceTests.swift:253 `回前台应恢复搜索` 恒红。改成"扫描意图 wantsScanning 与
#     执行状态 isScanning 分离"，挂起时一并归位。该类在 production 里目前还没有构造点（只有测试
#     new 它），所以这修的是潜在缺陷，不改变现有 App 行为。
#   - MCPServerTests.swift:466 那条是用例 bug，不是产品 bug：它拿 `calculate` + `###invalid###`
#     想触发执行错误，而 CalculateTool 把这类失败写成 `return "错误：表达式无效"`
#     （ToolRegistry.swift:302）根本不抛，走的仍是成功分支，`isError` 恒为 false——那条断言
#     从来没可能碰到 MCPServer 的 catch 分支。改成白名单放行一个未注册的工具，让
#     `ToolRegistry.execute` 真抛 NSError，并把透传文案一起钉住。
#   本地验证（-only-testing 那 4 个类，CI 同款 -test-timeouts-enabled + 30/60 allowance）。macOS：
#   EOF 补发落地前那轮还剩 SSETransportTests 8 tests 2 failures + MCPClientTests 28 tests 2 条断言
#   失败；补发之后 132 tests 0 failures，5 条锚点方法 0.001–0.241s 全过，新增端口用例 0.021s。
#   iOS：同样 4 个类 80 tests 0 failures，5 条 0.001–0.155s、新端口用例 0.002s，日志里同样出现
#   `[MCPSecurity] 检测到 MCP endpoint 劫持尝试：SSE=http://localhost/sse, endpoint=http://localhost:9999/messages`
#   ——两个平台都是"事件真的进到同源校验里、然后被端口口径拒掉"，不是靠丢事件蒙过断言。
# - 证据：main@7ccc5ac + PR #56 的 f71be62 / ea16a7e / 4183bd6 / 153b8a8 / bb3b793 / f74e07a 共七轮 run
#   （产品代码完全相同，只有本基线文件在变）的全部 test job 日志与后六轮闸门自身的 NEW FAILURE
#   明细；再加 #56 落地后的 main@632e087、#57 的 9147076、main@5090a91 三轮 iOS job 日志——
#   上面那条"耗时压在 allowance 临界值"的判断就来自这十轮的逐方法耗时矩阵；
#   收录门槛是跨轮复现 >=2 次，或确定性断言失败（1 次也收），或已出现在闸门明细/上一版基线里。
#   XCUITest 的 `Failed to terminate/launch com.aether.app.ios` 属 XCUITest runner 噪声、
#   xcresult 不计失败，不收。
# - main@c2005ea（PR #55 之前）里出现过、之后四轮都不复现的失败不收录——那是已经还掉的债，
#   例如 DesignSystemTests/testAetherIconAllCasesCount。
# - 首轮锚定（#56）收录的每一条都早于那次改动：那次只动 ci.yml 与 scripts/，没碰产品与用例代码。
#   它们此前被 `grep -c '"failed"'` 这个恒为 0 的旧门静默放行。
